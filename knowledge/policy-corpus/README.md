## 원문 보존 기준

- 고객 검색 본문에 새로운 정책·요약·번역·추정 예시를 쓰지 않았다. 제목·문단·목록·표는 원문 줄 범위를 그대로 발췌했다.
- 결합 시 빈 줄을 넣고 CRLF를 LF로 정규화한 것 외에는 발췌 문자열을 변경하지 않았다.
- [selection.json](selection.json)에 네 원본 파일의 SHA-256, 원본 커밋, 정책별 포함·부분 포함·제외·보류 이유와 모든 발췌 줄 범위를 기록했다.
- [manifest.json](manifest.json)에 발췌 조각과 산출 파일의 SHA-256을 기록했다. 원문이 바뀌면 생성 도구는 기존 선택 명세로 계속 진행하지 않는다.
- 조건과 예외가 구현 설명과 같은 원문 문단에 섞여 있으면 문장을 재작성해 분리하지 않고 해당 문단을 유지했다. 모든 문장이 고객용 말투로 바뀐 FAQ는 아니다.
- 정책의 마지막 확정일을 `effectiveFrom`으로 자동 치환하지 않았다.

## 전수 분류와 검수 보완

네 정책 문서에서 정책 ID가 있는 제목 **225개**를 전수 분류했다. 본문 단위 포함 57개, 일부 원문 발췌 13개, 범위 제외 153개, 충돌 보류 2개다. 관련 정책 목록·결정 이유를 제외한 경우도 명세에 기록했다. 정책 ID가 없는 구독 소개·용어·현재 정책 상위 제목은 별도 원문 범위로 포함했다.

검수에서 발견하고 보완한 사항:

1. 초기 주제 목록에서 빠졌던 비대면 약관, 대구 배송지 제한, 재신청·중복 구독, 결제수단 변경·삭제를 포함했다.
2. 품질 문의 `OTHER`가 주문·상품·배송과 연결되지 않아도 된다는 예외 문장을 복원했다.
3. 완료 사진의 고객 조회 권한과 고객 서명·인증번호 미수집 문장의 발췌 줄 범위를 수정했다. 원문 문장을 수정한 것이 아니다.
4. 고객 알림 18종, 자체 배달, 로그인 만료·로그아웃·외부 장애와 개인정보 권리행사 범위를 추가 발췌했다.
5. 환불 예시의 “앞의 월요일 1명…”이 가리키는 할인 계산 예시가 같은 파일에 먼저 나오도록 `POL-PAYMENT-009`를 환불 파일 앞에 배치했다. 중복 복사하거나 원문의 지시어를 고치지 않았다.
6. 원문처럼 `###`로 시작하는 제목을 읽을 때 이전 정책의 제목이 다음 정책 경로에 누적되는 Markdown extractor 문제를 수정했다. 원문 제목 레벨은 유지했다.
7. 구독 소개의 “핵심 용어” 제목이 다음 정책의 부모로 잘못 남지 않도록 원문의 `## 4. 현재 정책` 제목도 발췌했다.

최종 검수에서 미분류 정책 제목은 0개다. 취소 14시 경계·진행 중 결제·환불 부분 성공·할인·첨부·문의 예외 등 별도 선정한 핵심 조건 29개가 산출물에 존재하는지 검사했다. 이 수치는 실제 고객 질의에 대한 검색·답변 품질 검증 결과를 뜻하지 않는다.

## 제외 및 원문 충돌

- `AUTH-POL-WD-003`, `AUTH-POL-SUB-002`의 “사용자 직접 구독 해지 기능은 제공하지 않는다”는 표현은 구독 서비스 `POL-SUBSCRIPTION-003`과 충돌한다. 해당 Auth 두 조항을 적재에서 보류했다. 어느 원문도 고치거나 충돌이 해결됐다고 처리하지 않았다.
- `POL-PAYMENT-004`의 관련 정책 설명이 정기결제에 반영 기준일을 적용하는 것처럼 읽히지만 `POL-SUBSCRIPTION-013` 본문은 정기결제를 제외한다. 관련 정책 목록을 발췌하지 않았고 본문의 적용 대상·예외를 유지했다. 원문 정정은 하지 않았다.
- `DLV-POL-FAILURE-002`의 내부 실패 사유 코드는 `DLV-POL-VIEW-001`의 고객 비공개 규칙에 따라 제외했다. 고객용 표시 문구는 원문 그대로 포함했다.
- API·인증·DB·Kafka·관리자/기사 운영·모델 설정·지식 처리 운영 등의 내부 규칙은 고객 지식 범위에서 제외했다. 실제 FAQ 질문·답변 목록은 이번 정책 원본에 없으므로 만들지 않았다.
- 미확정 보관 온도·시간을 채우지 않았다. 미확정이라는 원문 제한을 유지했다.
- 정책 본문만으로 개인별 배송 상태·결제 결과·실제 환불 완료를 알 수 없다. 해당 상태 조회는 이 정적 지식 묶음에 포함되지 않는다.
- 테스트 예시인 “7일 이내 환불”은 발췌 파일에 없다.

## 실제 업로드가 남은 이유와 재개 조건

[upload-status.json](upload-status.json)에 적재 전 점검 결과를 남겼다. 로컬 기본 주소의 Customer `8084`, AI `8000`, MinIO `9000` 헬스체크는 모두 연결 시간 초과였다. 다른 주소의 원격 환경 상태는 아직 확인하지 못했다. 로컬 Python에는 `sentence_transformers`와 `transformers`가 없고 Chroma만 설치되어 있었다.

필요한 정보는 **실제 대상 Gateway 주소, 관리자 인증을 읽을 로컬 환경변수명/파일 위치, 정책 적용일(KST)**이다. 토큰을 채팅이나 보고서에 기록하지 않는다. 임의 관리자 ID·역할 헤더로 접근하거나 정책 확정일을 적용일로 추정하지 않는다.

환경이 확인되면 기존 `POST /api/customer/admin/knowledge/versions`에 파일과 `sourceService`, `documentKey`, `category`, `title`, `version`, `effectiveFrom`을 multipart로 제출한다. 응답의 실제 versionId로 기존 조회 API에서 상태를 추적하고, Customer→AI 작업 및 callback을 거쳐 처리 상태·청크 수를 확인한다. 현재 구현은 조건에 따라 자동 활성화되므로 대상과 적용일 확인이 필요하다. 실패 시 동일 파일을 맹목적으로 재등록하지 않고 기존 버전 상태부터 확인한다.

지금은 실제 업로드·임베딩·활성 버전 검색 검증이 끝나지 않았으므로 전체 작업 완료로 표시하지 않는다.
