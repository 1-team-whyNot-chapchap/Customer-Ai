### 1.1 자체 배달 — `DLV-POL-PRINCIPLE-001`

챱챱이 직접 생산한 도시락은 챱챱 소속 배달기사가 배송한다. 외부 배송업체, 계약 기사와 가맹점 배송은 MVP에서 사용하지 않는다.

### 3.2 배송 시간대 — `DLV-POL-SLOT-001`

모든 업무 시각은 KST(`Asia/Seoul`)를 기준으로 한다.

| 코드 | 고객 약속 시간 |
|---|---|
| `LUNCH` | 11:00~13:00 |
| `DINNER` | 17:00~19:00 |

### 10.2 전달 방식 — `DLV-POL-COMPLETE-002`

완료 시 다음 전달 방식 중 하나를 필수로 기록한다.

| 코드 | 의미 | 조건 |
|---|---|---|
| `DIRECT` | 고객 또는 수령인에게 직접 전달 | 고객 직접 입력 없음, 필수 비대면 보관 약관 적용 |
| `DOORSTEP` | 문 앞에 비대면 보관 | 필수 비대면 보관 약관과 완료 사진 적용 |
| `OTHER` | 경비실·무인택배함 등 고객이 직접 입력한 문 앞 외 비대면 보관 | 고객 보관 요청 원문, 실제 보관 장소와 완료 사진 필수 |

서버는 `OTHER` 고객 보관 요청 원문이 비어 있는 요청을 거절한다. `OTHER`는 직접 전달을 표현하지 않는다. 비대면 보관 동의는 서비스 이용 또는 구독 신청 시 필수 약관으로 받고, 배달 방식별 선택 동의는 다시 받지 않는다. Subscription-Service는 약관 동의 원본을 소유하고 동의 여부와 동의 시각을 보존한다. Delivery-Service는 고객별 배송 기록에 동의 여부와 동의 시각을 저장하며 별도 약관 버전은 저장하지 않는다. 일반 자유 입력 배송 메모는 MVP 주문 이벤트에 포함하지 않는다.

### 10.3 완료 증빙 범위 — `DLV-POL-COMPLETE-003`


- `DIRECT`는 별도 사진 없이 완료할 수 있다.
- `DOORSTEP`은 실제 보관 장소와 완료 사진이 있어야 `DELIVERED`로 변경할 수 있다.
- `OTHER`는 고객의 문 앞 외 비대면 보관 요청 원문, 실제 보관 장소와 완료 사진을 필수로 기록한다.

- 저장 완료 사진은 비공개 저장소에 보관하고 해당 고객과 업무상 필요한 관리자만 조회한다. 기사는 완료 후 저장된 사진을 다시 조회하는 API 권한을 갖지 않는다.

- 고객 서명과 인증번호는 MVP에서 수집하지 않는다.

### 11.1 고객 부재 절차 — `DLV-POL-ABSENCE-001`

1. `DOORSTEP`은 필수 비대면 보관 약관 동의와 안전한 보관 가능 여부를 확인하고 문 앞에 보관한다.
2. `DIRECT` 고객이 부재하면 고객에게 1회 연락한다.
3. 연락되지 않으면 고정 대기시간 없이 안전한 비대면 보관 가능 여부를 판단한다.
4. 유효한 필수 약관 동의와 안전한 장소가 있으면 문 앞 또는 안전한 장소에 보관한다.
5. 비대면 보관은 실제 보관 장소와 완료 사진을 기록하고 `DOORSTEP` 또는 `OTHER`로 `DELIVERED` 처리한다. 최초 선택 `DIRECT`는 별도로 보존한다.
6. 고객과 연락되어 대기에 합의한 경우만 현장 판단으로 짧게 대기할 수 있다. MVP에서 고정 타이머를 구현하지 않는다.
7. 유효한 필수 약관 동의를 확인할 수 없거나 접근·안전 문제로 보관할 수 없으면 물품을 회수하고 `FAILED`로 처리한다.
8. 연락 시도 여부·시각·결과, 실제 전달 결과, 회수 여부·시각과 실패 사유를 기록한다.

### 11.2 고객 사전 안내 — `DLV-POL-ABSENCE-002`

구독 또는 배송 조건 설정 화면에 다음을 안내한다.

- 주소·전화번호·공동현관 정보가 잘못되거나 누락되면 배송에 실패할 수 있다.
- 서비스 이용 또는 구독 신청 시 비대면 보관 가능성, 고객 부재·연락 불가 시 안전한 장소 보관, 보관 불가 시 회수·실패 처리와 비대면 완료 사진 촬영을 필수 약관으로 안내하고 동의받는다.
- 필수 약관에 동의하지 않으면 구독 신청과 배송 이용을 완료할 수 없다.
- `DIRECT`, `DOORSTEP`, `OTHER` 선택 시 배달 방식별 선택 동의는 다시 받지 않는다.
- `OTHER`는 경비실·무인택배함 등 문 앞 외 비대면 보관 요청을 고객이 직접 입력해야 한다.
- 문 앞에 놓인 도시락은 고객이 즉시 수령하고 안내된 방법으로 보관해야 한다.
- 고객 부재 시 1회 연락하고, 연락되지 않으면 고정 대기 없이 안전한 보관 완료 또는 물품 회수 실패로 처리한다.
- `DIRECT` 고객이 연락되지 않으면 안전한 장소에는 사진을 남기고 완료하며, 안전하게 보관할 수 없으면 물품을 회수하고 실패 처리한다.
- 배송 실패 회차는 재배송하지 않고 부분 환불한다.

### 11.3 신선도 안전 제한 — `DLV-POL-ABSENCE-003`

- 검증된 포장·계절·외기온도 기준 없이 도시락을 외부 공용공간에 장시간 방치하지 않는다.
- Delivery-Service는 제품별 보관 온도, 비대면 보관 허용시간, 보냉 유지시간을 임의로 계산하거나 판정하지 않는다.
- 구체적인 보관 온도·허용시간·계절별 보냉 기준은 생산·포장·품질 검증 후 해당 업무 영역의 정책으로 확정한다.
- 검증 기준이 확정되기 전에는 기사 화면에 임의의 숫자 기준을 제공하지 않고, 눈에 보이는 장소 안전 조건과 고객의 비대면 보관 동의만 확인한다.

### 11.4 보관·섭취 안내 — `DLV-POL-ABSENCE-004`

고객에게 제공하는 식품 보관 안내와 비대면 보관 동의는 목적을 구분한다.

- 제품별 보관방법과 소비기한 등 식품 자체의 안전 정보는 상품·생산·품질 등 해당 원본 영역이 확정한다.
- 고객은 구독·주문 과정과 배송 완료 이후 해당 제품에 적용되는 보관방법과 소비기한을 확인할 수 있어야 한다.
- 제품별 보관방법과 소비기한 안내는 정보 제공이 목적이므로 별도의 필수 체크박스 동의를 추가하지 않는다.
- 비대면 보관 가능성, 고객 부재 시 안전한 장소 보관, 완료 사진 촬영, 보관 불가 시 회수·실패 처리와 신속한 수령 필요성은 기존 필수 비대면 보관 약관에 포함한다.
- 배송 완료 후에는 고객이 상품을 신속히 수령하고 제품에 표시되거나 서비스에서 제공된 보관방법을 따르도록 안내한다.
- Delivery-Service는 제품별 보관방법·소비기한 원본을 소유하거나 수정하지 않으며, 식품 안전 수치를 배송 상태 판단 기준으로 임의 사용하지 않는다.

### 12.3 실패 이후 처리 — `DLV-POL-FAILURE-003`

- `FAILED`는 최종 상태이며 관리자도 다른 배송 상태로 되돌릴 수 없다.
- 실패 사유나 메모의 정정만 허용하되, 원본 값을 덮어쓰지 않고 정정 전·후 값과 정정 사유, 처리 관리자와 처리 시각을 이력으로 남긴다.
- Delivery-Service는 환불액을 계산하거나 결제를 취소하지 않고 재배송을 만들지 않는다.
- 실패는 해당 고객의 해당 배송 회차에 연결하여 기록한다.
- 물품을 회수한 실패는 회수 여부와 회수 시각을 함께 기록한다.
- 한 회차의 실패를 전체 구독 실패로 취급하지 않는다.
- 실패 회차는 부분 환불 대상으로 확정하고 Subscription-Service가 환불액을 계산·실행한다.
- 실패 회차를 환불 대상으로 최종 확정하면 `DELIVERY_REFUND_CONFIRMED`를 `reasonCode=DELIVERY_FAILED`로 발행한다.
- Delivery-Service는 환불 수량·금액을 계산하지 않고 Subscription-Service가 저장된 주문 배분금액으로 환불한다.

### 13.1 지연 판정 — `DLV-POL-DELAY-001`

- 고객별 배송 대상 단위로 판단한다.
- 별도 `DELAYED` 상태를 만들지 않는다.
- KST 서버 시각이 점심 `13:01:00`, 저녁 `19:01:00` 이상이고 대상이 미완료이면 1분 지연이다.
- 진행 중에는 조회 시 `isDelayed`를 계산한다.
- 완료 시 `deliveredAt`과 약속 종료 시각을 비교하여 `wasDelayed`와 분 단위 지연 시간을 저장한다.
- 점심 `13:00:59`, 저녁 `19:00:59`까지 완료하면 정상이고 그 이후 완료하면 지연이다.
- 늦게 완료해도 상태는 `DELIVERED`다.

### 13.2 지연 사유와 후속 처리 — `DLV-POL-DELAY-002`

- Delivery-Service는 지연 사유, 발생 시각과 지연 시간을 기록한다.
- 점심 13:01, 저녁 19:01에 미완료 대상을 한 번 확인해 지연을 기록하고 Customer-Service를 통해 고객에게 지연 사실을 안내한다.
- 일반 지연은 배송을 계속 진행하고 해당 회차를 환불 처리한다. 늦게 정상 전달하면 배송 상태는 `DELIVERED`로 유지한다.
- 천재지변 등 안전하게 배송을 계속할 수 없는 사유는 고객에게 사유와 취소 사실을 안내하고 배송 대상을 `FAILED`로 종료한다. Subscription-Service는 해당 배송 회차를 취소하고 환불한다.
- Delivery-Service는 지연·취소 사유와 배송 실행 결과를 Subscription-Service에 전달하지만 환불액을 계산하거나 결제를 취소하지 않는다.
- 지연 및 천재지변 환불액 산식은 Subscription-Service 정책으로 결정한다.
- 일반 지연은 배송을 완료하고 환불 대상으로 최종 확정한 뒤 `reasonCode=DELIVERY_DELAYED`로, 천재지변 취소는 `reasonCode=FORCE_MAJEURE_CANCELED`로 `DELIVERY_REFUND_CONFIRMED`를 발행한다.
- Customer용 `DELIVERY_DELAYED` 알림 Event만으로는 환불하지 않는다.
- 같은 배송 공개 UUID에는 환불 확정 Event를 한 번만 발행한다. 이미 발행한 뒤 다른 사유가 확인되어도 새 환불 확정 Event를 발행하지 않는다.
- 여러 환불 사유가 동시에 해당하면 최종 실행 결과를 기준으로 대표 사유 하나만 선택한다. 늦게 완료하면 `DELIVERY_DELAYED`, 일반 실패로 종료하면 `DELIVERY_FAILED`, 천재지변으로 취소·실패 종료하면 `FORCE_MAJEURE_CANCELED`를 사용한다.
- Delivery-Service와 Subscription-Service는 `REFUND:DELIVERY:{deliveryId}`를 환불 업무키로 사용하며 `reasonCode`를 업무키에 포함하지 않는다.
- 점심 13:30, 저녁 19:30에도 `READY` 또는 `DELIVERING`인 대상은 별도 상태를 만들지 않고 관리자 미종결 조회 목록에 표시한다. 자동 실패 처리하지 않고 기사·고객·증빙을 확인해 정상 완료 또는 실패 절차를 수행한다. 단말·통신·앱·서버 장애가 확인된 경우에만 `ADMIN_RECOVERY`를 사용한다.

### 14.1 마이페이지 조회 — `DLV-POL-VIEW-001`

MVP에서는 고객이 마이페이지에서 본인의 배송 상황을 확인한다.

표시 정보:

- 배송일과 점심·저녁 시간대
- 본인의 고객별 배송 상태
- 진행 중 지연 여부
- 완료 시각
- 전달 방식
- 실패 시 고객용 안내 문구: `배송을 완료하지 못했습니다. 해당 배송 회차는 환불 대상입니다.`

내부 실패 코드, 관리자 메모, 기사 메모, 담당 기사 개인정보와 다른 고객의 정보는 노출하지 않는다. 같은 전체 배송에 실패가 있어도 본인의 대상이 `DELIVERED`이면 `배송 완료`로 표시한다.

고객 표시 문구:

| 고객별 상태 | 기본 표시 |
|---|---|
| `READY` | 배송 준비 완료 |
| `DELIVERING` | 배송 중 |
| `DELIVERING` + 지연 | 배송이 지연되고 있습니다 |
| `DELIVERED` | 배송 완료 |
| `FAILED` | 배송 실패 |

Delivery-Service의 고객 조회에서 `FAILED` 상세 안내는 실패 코드별로 세분화하지 않고 `배송을 완료하지 못했습니다. 해당 배송 회차는 환불 대상입니다.` 한 문구만 사용한다. 내부 `failure_code`와 기사·관리자 메모는 고객에게 공개하지 않는다. Customer-Service가 소유하는 알림 템플릿·앱 내 알림 문구는 이 조회 문구와 별도 계약이며 Delivery-Service가 변경하지 않는다.
